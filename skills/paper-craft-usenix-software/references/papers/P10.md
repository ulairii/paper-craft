# P10: FuzzGen: Automatic Fuzzer Generation

Kyriakos Ispoglou; Daniel Austin; Vishwath Mohan; Mathias Payer. **USENIX Security 2020**. [Official paper](https://www.usenix.org/conference/usenixsecurity20/presentation/ispoglou) · [Full text](https://www.usenix.org/system/files/sec20-ispoglou.pdf).

Source locations: Sections 1–7; MPEG2 initialization example, graph construction, Tables 2–3; Appendices A–D.

## Writing move: Explain automation by showing which expert knowledge is recovered

FuzzGen starts with a missing entry point: a library requires valid sequences of API calls and shared state before interesting code can execute. Existing consumers provide examples of that knowledge. The MPEG2 initialization example keeps the sequence and shared context while omitting distracting casts and field assignments. An API-dependence graph then connects observation to generated drivers.

## Experimental logic

Comparisons with manually written drivers address both automated generation and reachable behavior. Broader coverage and concentrated bug discovery can move differently: some manual drivers find more bugs in a narrow component. The consumer-count study explains why combining more examples eventually increases complexity without comparable API gains. Repeated frames also explain why fewer executions can reach deeper decoder state.

## Detail placement

Keep the library/consumer source requirements, consumer selection, argument reuse, and graph-merging assumptions visible. Generation is automatic, but the evaluated drivers were manually checked for valid API sequences. Full argument-attribute tables and device setup can move later. The appendix’s socket example is useful when explaining merging imprecision.

## Interpretation

The evaluated scope is seven codec libraries on Android and Debian. A 54.94% versus 48.00% coverage comparison differs by 6.94 percentage points. Some libraries favor manual drivers, and the CVE collection includes a duplicate. Sell reduced driver-writing effort and broader API exploration without equating every generated crash with a new exploitable vulnerability.
