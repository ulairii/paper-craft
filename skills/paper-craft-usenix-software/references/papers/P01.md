# P01: QSYM : A Practical Concolic Execution Engine Tailored for Hybrid Fuzzing

Insu Yun; Sangho Lee; Meng Xu; Yeongjin Jang; Taesoo Kim. **USENIX Security 2018**. [Official paper](https://www.usenix.org/conference/usenixsecurity18/presentation/yun) · [Full text](https://www.usenix.org/system/files/conference/usenixsecurity18/sec18-yun.pdf).

Source locations: Sections 1–6; bottleneck microbenchmarks, hybrid-fuzzing comparisons and pruning analyses.

## Writing move: Start with the measured bottleneck, then explain the specialization

QSYM makes the execution engine, rather than only constraint solving, the center of a scalability story. A measurement without symbolic branches or solver calls makes that choice understandable. The design then relaxes expensive analysis because the surrounding fuzzer can validate candidate inputs concretely. This is a contribution through specialization: a concolic engine designed for a particular workflow, with the workflow explaining the design.

## Experimental logic

Real-program bug findings establish practical value; microbenchmarks and component experiments explain the speed. Equal-core hybrid comparisons distinguish the system from simply adding workers. Concrete validation connects an optimistic analysis decision to useful generated inputs. Different benchmark families answer different questions: injected bugs, supplied proof-of-vulnerability seeds, and new real-program findings should have separate interpretations.

## Detail placement

Keep the execution/solver split, concrete validation, pruning policy, and supported instruction semantics close to the method. Explain that supplied vulnerability-triggering seeds change what a CGC experiment demonstrates. Full instruction-support inventories and routine configuration details can follow the central design argument.

## Interpretation

A fast execution component need not produce the same end-to-end speedup when solving dominates. Pruning and relaxed constraints trade completeness for throughput. Thirteen discovered bugs are not thirteen assigned CVEs. Historical exposure to OSS-Fuzz is useful context, not a matched resource comparison. The contribution is a practical hybrid engine rather than a universally sound analysis.

## Original writing illustration

Before: Our revolutionary engine solves symbolic execution and defeats all existing fuzzers.

After: An execution engine specialized for hybrid fuzzing reduces analysis cost, while concrete replay lets the fuzzer use candidates produced under relaxed constraints.
