## Writing move: Turn a new target into a distinct technical problem

FuzzUSB begins with the gadget side of a familiar interface, then explains why reversing a host fuzzer is insufficient. Configuration, enumeration, and communication expose different inputs, and useful sequences depend on driver state. The SCSI example carries this observation through state extraction and input generation. A HID case shows why both channel control and state matter.

## Experimental logic

The baseline, multichannel variant, and complete stateful system separate two capability additions. Per-channel coverage and scheduled state transitions give the main gains an explanation. FreeBSD adaptation shows which idea transfers and which interface changes. Known-bug timing and new discoveries answer different practical questions.

## Detail placement

Keep local-app and host capabilities explicit; not every finding is a cable-only attack. Android drivers are ported into the test environment, and physical controller drivers are outside coverage. State machines abstract I/O locations rather than every kernel state. Full rule combinations, construction times, and discovery tables can follow the main channel-and-state example.

## Interpretation

The 34 reported new bugs include four host-side findings; seven received CVEs. The 50-fold figure compares time to match a baseline’s final bug count, not every individual detection time. Race conditions limit deterministic reproduction. The second-platform result establishes useful coverage improvement, not the absence of vulnerabilities in FreeBSD.
